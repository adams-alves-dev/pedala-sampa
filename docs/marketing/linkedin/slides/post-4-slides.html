A decisão

Pedir cadastro mataria a contribuição

Quem tem a informação certa é quem organiza o pedal.

E essa pessoa não vai criar uma conta num site que ela nunca viu para consertar o horário de saída dela.

Ou é fácil, ou não acontece

Então a fricção saiu do usuário e foi para as camadas de trás.

Camada 1

Honeypot: o 200 mentiroso

// server/api/suggestions.post.ts // bots preenchem o campo escondido; // respondemos 200 sem criar nada if (body?.website) { return { ok: true, id: 'ok' } }

Um campo escondido no formulário. Humano não vê, bot preenche.

A API responde 200 e não cria nada. O bot registra sucesso e vai embora feliz.

Custa 3 linhas e resolve o bot mais simples.

A ordem importa

O Zod roda antes do Turnstile

✗ Ordem errada

Checa o desafio → descobre que faltou um campo → devolve 400.

O token já foi queimado. O reenvio corrigido falha.

✓ Ordem certa

Valida os campos → só então checa o desafio.

Um 400 de validação não consome o token.

Por quê

O token do Turnstile é de uso único. Na ordem errada, a pessoa preenche tudo de novo e leva erro de novo — estando certa.

Ordem errada não quebra o teste. Quebra o usuário honesto.

Curadoria

Nenhuma automação minha publica

Dois tokens, não um

O público é read-only. A CLI de curadoria usa outro, separado.

Sem permissão de publish

De propósito. O máximo que a automação faz é criar rascunho.

Publicar é humano

No CMS, com o conteúdo na frente.

Quando a única forma de ir ao ar é alguém clicando, o pior caso de um bug na automação é rascunho sujo — nunca conteúdo errado em produção.
